# Yukti — Design and Testing Document

> **Disclaimer:** Yukti is a decision-support prototype for educational and demonstration
> purposes. It is not clinically validated, is not an approved clinical device, and is not
> a substitute for clinical judgment.

---

## 1. What Yukti is

Yukti is a clinical decision support tool for emergency department clinicians managing
early pregnancy presentations. A clinician enters what they know about a patient —
dating, ultrasound findings, clinical picture — and Yukti guides them through the
relevant clinical pathway, surfacing guideline-based recommendations with their sources
attached.

It is built as a web application: a React frontend, a Python (FastAPI) backend, and a
retrieval-augmented (RAG) knowledge base of clinical guidelines so the tool's answers
are grounded in cited sources rather than generated freely.

**Live application:** https://yukti-blue.vercel.app

---

## 2. Architecture overview

- **Frontend:** React (Create React App). Each clinical pathway is its own component
  (`EPLPathway.jsx`, `PULEctopicTab.jsx`, `MedicationAbortionPathway.jsx`,
  `ContraceptionPathway.jsx`, `REMSPathway.jsx`). A top-level `App.js` holds shared
  patient state and renders the active pathway.
- **Backend:** FastAPI (Python) exposing endpoints including `/api/chat` (the Ask Yukti
  assistant), `/api/interpret-us` (parses a pasted ultrasound report into structured
  fields), `/api/abortion-status` (state law data), and pharmacy/clinic lookup endpoints.
- **Knowledge base / retrieval:** A ChromaDB vector store holding 552 chunked clinical
  guideline document chunks. Queries are filtered by clinical pathway so each pathway only
  retrieves relevant sources. Embeddings generated by `sentence-transformers`
  (all-MiniLM-L6-v2).
- **AI assistant:** Claude Sonnet (Anthropic API) used for the Ask Yukti chat and
  ultrasound report interpretation.
- **Hosting:** Backend on Render (Web Service), frontend on Vercel. Both auto-deploy on
  push to `main`.

### High-level data flow

1. Clinician enters patient data in a pathway UI.
2. Shared patient state lives in `App.js`, passed to whichever pathway is active and to
   the Ask Yukti assistant.
3. When the assistant is queried, the backend retrieves matching guideline chunks from
   ChromaDB (filtered to the relevant pathway) and passes them with the question to
   Claude, which returns a cited answer.
4. The pathway UI applies clinical logic to the entered data and displays recommendations
   with citations.

## 3. Design decisions and the reasons for them

### 3.1 Single shared state object (state hoisting)

**Decision.** All shared patient data lives in one state object at the top level
(`App.js`), passed down to each pathway and to the assistant.

**Why.** A clinician often moves between pathways for one patient (e.g. starting in EPL,
realising it's a medication abortion case). Holding the data once means nothing is
re-entered when they switch — the data follows the patient, not the screen. It also gives
the assistant the same patient context the pathway sees.

### 3.2 Pathway-scoped retrieval with per-pathway metadata flags

**Decision.** Each document chunk carries boolean metadata flags for the pathways it
belongs to (`pathway_epl: "true"`, `pathway_mab: "true"`, etc.), and retrieval filters on
those flags.

**Why.** A clinician asking an EPL question should not get medication-abortion sources
mixed in. An earlier version stored pathways as a single joined string (`"mab,epl"`) and
filtered with exact-match, which silently excluded any document tagged to more than one
pathway. The fix was per-pathway boolean flags, because ChromaDB's filtering does not
reliably support substring matching on a combined string.

### 3.3 Sourced answers and "no grounded source" honesty

**Decision.** The assistant attaches the source to its answers, and when retrieval returns
nothing above a relevance threshold (cosine similarity < 0.3), it says so rather than
answering anyway.

**Why.** A clinician cannot act on an unsourced recommendation at the point of care.
Refusing to answer when there is no grounded source is a safety feature — a confident
answer with no basis is worse than none.

### 3.4 Clinical context injection into Ask Yukti

**Decision.** The patient's current clinical state (gestational age, ultrasound
impression, derived EPL conclusion, hCG values) is injected into the chat context
alongside the retrieved guideline passages.

**Why.** Without patient context, the assistant gives generic answers. With it, it can
say "given your MSD of 30mm with no embryo, this meets SRU 2013 criteria for definitive
EPL" rather than explaining the criteria in the abstract. The `buildClinicalContext()`
function in `App.js` also derives the EPL conclusion from raw measurements — so even if
the physician selected "PUL" as the impression but entered MSD 30mm with no embryo, the
assistant knows the SRU criteria are met.

### 3.5 "Suggest and confirm" routing, never silent auto-routing

**Decision.** The entry screen recommends a pathway based on entered data but always
shows why and lets the clinician override.

**Why.** Early pregnancy presentations are genuinely ambiguous, and routing depends on
clinical judgment. A tool that decides for the clinician and is wrong is more dangerous
than one that proposes and explains.

### 3.6 Separate clinical assessment and management pathway boxes (EPL)

**Decision.** The EPL tab separates the interpretation/conclusion box from the management
selection (expectant / medical / surgical) into two distinct sections.

**Why.** Clinically these are sequential decisions: first confirm what you're dealing
with, then decide how to manage it. Presenting them together created cognitive load and
made it easy to select management before the conclusion was clear.

### 3.7 Mobile-first wizard flow

**Decision.** On mobile, each pathway shows one step at a time with explicit "Mark step
done" progression rather than a scrollable form.

**Why.** ED physicians use tablets and phones at the bedside. A long scrollable form is
unusable on a phone under clinical conditions. One question at a time reduces cognitive
load and errors.

## 4. Testing

### 4.1 Testing methodology

Yukti's testing combines automated tests on the clinical and API logic with structured
manual testing of the full user flow.

**Automated tests** guard against two failure modes:
1. API endpoints returning wrong status codes or malformed responses
2. Clinical logic (SRU criteria, hCG thresholds, EC recommendations) drifting from the
   encoded guidelines

Each automated test encodes a specific clinical rule from a cited source and verifies
the code matches that rule. Tests were validated by deliberately breaking the code (e.g.
changing the 7mm CRL threshold to 6mm) and confirming the test caught it.

**Manual testing** covers the end-to-end user flow: entering patient data, walking a
complete pathway, and verifying the correct recommendation surfaces with its source.

## 5. Deployment

| Component | Platform | URL |
|-----------|----------|-----|
| Frontend | Vercel | https://yukti-blue.vercel.app |
| Backend API | Render (Starter plan) | https://yukti-api.onrender.com |
| Source code | GitHub | https://github.com/sv45/yukti |

**CI/CD:** GitHub Actions (`.github/workflows/ci.yml`) runs the full test suite on every
push to `main` — backend pytest suite and frontend Jest suite.

**Auto-deploy:** Both Vercel and Render are connected to the GitHub repo and redeploy
automatically on push to `main`.

### Deployment architecture decision: cloud vs on-premises

**Recommendation: cloud deployment.**

Yukti is deployed entirely on cloud infrastructure and this is the recommended approach
for any production use. The rationale:

- **Accessibility:** ED physicians need access from any device, any shift. Cloud
  deployment provides a stable public URL accessible from hospital workstations, tablets,
  and phones without VPN or institutional setup.
- **Maintenance:** A Python backend running sentence-transformers (a ~400MB ML model)
  requires consistent compute resources. Cloud platforms manage uptime, restarts, and
  scaling automatically.
- **Cost at current scale:** The current deployment uses Render's Starter plan ($7/month)
  for the backend and Vercel's free tier for the frontend — total cost under $10/month.
  This is appropriate for a prototype or small-team deployment.

### Deployment cost comparison

| Option | Platform | Monthly cost | Notes |
|--------|----------|-------------|-------|
| **Current (prototype)** | Render Starter + Vercel Free | ~$7/month | 512MB RAM; suitable for demo and low traffic |
| **Small production** | Render Standard + Vercel Free | ~$25/month | 2GB RAM; handles concurrent users reliably |
| **Institutional/scaled** | AWS EC2 t3.medium + S3 + CloudFront | ~$40–80/month | Full control, persistent storage, scalable |
| **On-premises** | Hospital server | High upfront + IT overhead | HIPAA-compliant infrastructure; appropriate for patient data integration |

**For a validated clinical tool handling real patient data**, on-premises or a
HIPAA-compliant cloud environment (AWS GovCloud, Azure Government) would be required.
The current cloud deployment is appropriate for demonstration and educational purposes
only, consistent with the tool's prototype status.

## 7. Known limitations

- **Not clinically validated.** Yukti has not undergone formal clinical validation and
  should not be used as the sole basis for patient care decisions.
- **Knowledge base scope.** Recommendations are limited to ingested guideline documents;
  emerging evidence not yet ingested will not surface.
- **No EHR integration.** Patient data must be re-entered; there is no connection to
  electronic health records.
- **Single-provider workflow.** The tool is designed for one clinician per session and
  does not support multi-provider or handoff workflows.
- **State law data currency.** Abortion legality data reflects the ingested dataset and
  may not capture recent legislative changes.
